- 2026-10-05 — Risk Engine Layer 1 & 2 Upgrade: two-layer fraud scoring (rule-based + Isolation Forest ML) now fully wired end-to-end.
  - **Layer 1 — RiskEngineClient.java (`microservices/transaction-service`):** Added `JdbcTemplate` injection. Added three best-effort DB enrichment queries before every `/score` call: `queryAccountAgeHours` (reads `ACCOUNT.created_date`, enables `new_account_under_24h` rule), `queryRecentTxCount` (counts non-failed `REMITTANCE` rows in last hour, enables velocity rules `high_velocity_over_5` / `medium_velocity_over_2`), `queryAmountVsAvgRatio` (30-day average from `REMITTANCE`, new behavioral signal). All three are null-safe and omitted gracefully on query failure. Previously these fields were designed into `scorer.py` but never sent — all three rules were dead code before this change.
  - **Layer 2 — `ml_scorer.py` (`microservices/risk-engine`):** New file. Isolation Forest anomaly detector — unsupervised, no labeled fraud data required. 10,000 synthetic training samples (9,000 normal + 1,000 anomalous across 4 archetypes: large off-hours transfer from new account, high-velocity small transfers, single transfer far above customer average, combined new-account + large + high-velocity). 6-dimensional feature vector: `amount_php`, `hour_of_day`, `account_age_hours`, `recent_tx_count`, `amount_vs_avg_ratio`, `is_new_recipient`. Model serialized to `/tmp/paypink_if_model.joblib` on first run (warm-start on subsequent container starts). `warm_up()` called at FastAPI lifespan startup to avoid slow first-request penalty. `ML_WEIGHT=0.90` — IF score is down-weighted so a borderline anomaly alone cannot reject a transfer without at least one rule signal also firing.
  - **scorer.py (`microservices/risk-engine`):** Added `amountVsAvgRatio` optional field to `ScoreRequest`. Added three new tiered ratio rules: `≥10x → +0.40`, `≥5x → +0.25`, `≥3x → +0.10` with dynamic reason strings (e.g. `amount_3.7x_above_customer_avg`). Updated docstring to document all active rules.
  - **main.py (`microservices/risk-engine`):** Complete rewrite to version 3.0.0. Added FastAPI `lifespan` context manager calling `warm_up()` at startup. Runs both scorers independently, applies `ML_WEIGHT` to IF score, combines with `max(rule_score, ml_weighted)`, deduplicates and merges reason lists (rule reasons first). Response now includes `ruleScore` and `mlScore` separately for observability/Grafana. OTel span attributes extended with `accountAgeHours`, `recentTxCount`, `amountVsAvgRatio`, `risk.rule_score`, `risk.ml_score`, `risk.combined_score`.
  - **requirements.txt (`microservices/risk-engine`):** Added `scikit-learn==1.5.2`, `numpy==1.26.4`, `joblib==1.4.2`.
  - **Dockerfile (`microservices/risk-engine`):** Added `COPY ml_scorer.py .` line (was missing; container would crash on import without it).
  - **Frontend visibility:** `bank.js` already reads `res.riskScore` and `res.riskDecision` from the remittance response and renders them on the transfer receipt screen (`"Risk evaluation: Score 0.40 (APPROVED)"`). The combined score from the new two-layer engine flows through unchanged — no frontend changes needed.
  - **Contract unchanged:** `RiskResult{score, decision, reasons}` consumed by `RemittanceOrchestratorService` is identical. `ruleScore`/`mlScore` are extra response fields ignored by the Java client. Existing tests (`RemittanceSagaTest`, `InternalTransferTest`) use `mock(RiskEngineClient.class)` — unaffected by the `JdbcTemplate` constructor addition. — [dom]
