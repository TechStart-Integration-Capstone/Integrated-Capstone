- 2026-10-06 — Loan disbursement fixes + credit limit.
  - **Loan not recorded (LOAN / LOAN_SCHEDULE empty, application stuck DECIDED):** accept ran inside one DB transaction wrapping the transaction-service call with a 3 s client timeout; a slow transfer rolled back LOAN/LOAN_SCHEDULE/ACCEPTED while the money still posted. `LoanDisbursementService` now claims the offer first (status `DISBURSING`, committed before money moves), then transfers and records the loan. New `recoverDisbursements()` job (every 30 s, `loan.disbursement-recovery-ms`) finishes `DISBURSING` applications, and DECIDED ones whose `LOAN-DISB-{ref}` remittance already exists (heals existing stuck data), reusing the fixed transfer key so money moves at most once. A definitive REJECTED marks the application `FAILED` (422 `disbursement-failed`). Orchestrator timeout 3 s → 10 s (`app.orchestrator.timeout-ms`).
  - **Saga worker broken by the status rename:** `recordT24Posted` now writes `Processing` (internal_status `POSTED`) but `RemittanceSagaWorker` still looked for `T24_POSTED`, so T24-posted transfers whose ledger commit failed stayed `Processing` forever. Worker now treats `Processing` + internal_status `POSTED` (or legacy `T24_POSTED`) as T24-posted → ledger commit; other `Processing` rows → T24 inquiry then commit. Rows touched in the last 15 s are skipped (orchestrator still working on them).
  - **Doubled loan entries in transaction history:** `RemittanceLedgerService.commitLedgerMutation` was not idempotent — the orchestrator and saga worker could both commit one remittance (two LEDGER_TRANSACTION rows, double credit). It now locks the REMITTANCE row (UPDLOCK) and replays without posting if the ledger row already exists, healing a stale status. `findTransactionId` tolerates pre-existing duplicate rows. Existing duplicates are not removed.
  - **Credit limit from credit history:** the credit-score band max (LOW 30k / NORMAL 250k / HIGH 1M) is now the customer's total limit; outstanding principal on open loans plus `DISBURSING` offers is taken off it. Apply caps the offer at what is left (COUNTER_OFFER) or declines `CREDIT_LIMIT_REACHED`; accept re-checks (409 `credit-limit-reached`) so side-by-side offers cannot exceed it. New `LoanCreditLimitService`, `GET /api/v1/loans/eligibility`.
